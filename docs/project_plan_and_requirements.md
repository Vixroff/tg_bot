# План проекта и требования

## 1. Что представляет собой проект сейчас

`kosten_bot` - это сервис продажи рыболовных товаров с текущей архитектурой под Telegram Mini App:

- бот на `aiogram` регистрирует пользователя и открывает магазин;
- backend на `FastAPI` отдает API каталога, заказов, оплаты и админских операций;
- frontend на `React + Vite` подключается как Mini App;
- данные хранятся в PostgreSQL через `SQLAlchemy` и `Alembic`.

Фактически в коде уже реализованы основные сущности интернет-магазина:

- пользователи;
- товары;
- заказы и позиции заказа;
- платежи;
- админские операции по товарам и заказам.

Важно: текущая реализация ориентирована на Telegram (`telegram_id`, Telegram bot, Telegram Mini App). Ниже требования сформулированы так, чтобы проект можно было развивать в сторону интеграции с сообществом или каналом VK с аудиторией около 800 пользователей.

## 2. Цель проекта

Создать цифровую витрину и канал продаж для небольшого рыболовного бизнеса, где пользователь приходит из социальной платформы, открывает магазин, выбирает товары, оформляет заказ, оплачивает его и получает уведомления о статусе.

Для следующего этапа развития целевая интеграция:

- входной трафик из VK;
- аудитория до 800 зарегистрированных пользователей;
- сценарий периодических пиков после публикаций в канале или сообществе;
- сохранение текущей backend-модели магазина как ядра системы.

## 3. Предлагаемый план проекта

### Этап 1. Стабилизация текущего MVP

Цель: довести до устойчивого состояния уже существующий магазин.

Задачи:

- привести в порядок пользовательские сценарии бота и Mini App;
- завершить базовую админку товаров и заказов;
- определить единый способ идентификации пользователя;
- заменить тестовую оплату на интеграцию с реальным платежным провайдером или описать промежуточный ручной процесс;
- доработать тексты, статусы, ошибки и системные сообщения;
- настроить базовый мониторинг и логирование.

Результат этапа:

- рабочий MVP магазина;
- понятные пользовательские и административные сценарии;
- готовность к интеграции с внешним каналом привлечения.

### Этап 2. Подготовка к мультиканальной интеграции

Цель: отвязать бизнес-логику магазина от Telegram-специфики.

Задачи:

- заменить зависимость от `telegram_id` на более общую модель внешней идентичности пользователя;
- ввести слой интеграций с каналами привлечения (`telegram`, `vk`, потенциально web`);
- выделить сценарии входа, регистрации и повторной авторизации;
- определить способ передачи контекста пользователя из VK в backend;
- описать события: переход из публикации, открытие витрины, создание заказа, оплата, уведомление.

Результат этапа:

- backend готов к работе не только с Telegram;
- упрощается подключение VK без ломки доменной модели заказов и каталога.

### Этап 3. Интеграция с VK

Цель: подключить VK как полноценный канал продаж.

Задачи:

- определить формат присутствия в VK: сообщество, канал, мини-приложение, ссылки на web storefront;
- реализовать авторизацию или безопасную идентификацию пользователя из VK;
- обеспечить переход из постов и закрепленных материалов к витрине;
- добавить сценарии уведомлений о заказе через доступные VK-механизмы или альтернативный канал;
- адаптировать контент и CTA под VK-аудиторию;
- подготовить операционные инструкции для администратора.

Результат этапа:

- пользователи из VK могут открыть магазин и оформить заказ;
- администратор понимает, как сопровождать поток заказов из VK.

### Этап 4. Масштабирование и операционная готовность

Цель: обеспечить устойчивую работу на целевой аудитории и при маркетинговых пиках.

Задачи:

- ввести наблюдаемость по API, платежам и заказам;
- ограничить злоупотребления и всплески запросов;
- настроить резервное копирование БД;
- ввести регламент поддержки и обработки ошибок;
- добавить аналитику конверсии по воронке.

Результат этапа:

- система контролируемо работает на аудитории до 800 пользователей;
- понятны узкие места и метрики роста.

## 4. Функциональные требования

### 4.1. Пользовательские функции

Система должна позволять пользователю:

1. Открыть витрину магазина из внешнего канала коммуникации.
2. Идентифицироваться в системе через внешний источник (на текущем этапе Telegram, в целевой версии также VK).
3. Просматривать список активных товаров.
4. Открывать карточку товара с названием, описанием, ценой, единицей измерения, категорией и изображением.
5. Формировать заказ из одной или нескольких товарных позиций.
6. Указывать количество по каждой позиции.
7. Видеть итоговую стоимость заказа до подтверждения.
8. Создавать заказ и получать его уникальный номер.
9. Оплачивать заказ через платежный сценарий системы.
10. Просматривать список своих заказов.
11. Просматривать статус конкретного заказа.
12. Получать уведомление или понятный статус после успешной либо неуспешной оплаты.

### 4.2. Функции каталога

Система должна:

1. Хранить каталог товаров с признаком активности.
2. Исключать неактивные товары из пользовательской витрины.
3. Поддерживать категории товаров.
4. Поддерживать хранение изображения товара.
5. Использовать зафиксированную цену товара на момент оформления заказа.

### 4.3. Функции заказов

Система должна:

1. Создавать заказ только для валидного пользователя.
2. Создавать заказ только из доступных активных товаров.
3. Проверять, что количество каждой позиции больше нуля.
4. Сохранять состав заказа и цену каждой позиции на момент покупки.
5. Рассчитывать общую сумму заказа автоматически.
6. Поддерживать статусы заказа: `requires_payment`, `paid`, `processing`, `shipped`, `delivered`, `cancelled`.
7. Давать пользователю доступ только к собственным заказам.

### 4.4. Функции оплаты

Система должна:

1. Создавать платежную сущность, связанную с заказом.
2. Хранить сумму, провайдера, внешний идентификатор и статус платежа.
3. Поддерживать как минимум статусы `pending`, `paid`, `failed`, `cancelled`.
4. После успешной оплаты переводить заказ в статус `paid`.
5. Исключать повторную неконсистентную оплату одного и того же заказа.

### 4.5. Административные функции

Система должна позволять администратору:

1. Просматривать полный список товаров, включая неактивные.
2. Создавать товар.
3. Изменять данные товара.
4. Деактивировать товар без физического удаления истории заказов.
5. Просматривать список всех заказов.
6. Изменять статус заказа.
7. Просматривать список пользователей.
8. Выполнять административные действия только при наличии прав администратора и защищенного токена.

### 4.6. Функции интеграции с VK

Для целевой версии с VK система должна:

1. Принимать переход пользователя из публикации, меню сообщества или закрепленной ссылки VK.
2. Передавать в storefront источник перехода и campaign-метки.
3. Идентифицировать пользователя VK без необходимости ручного ввода данных на каждом входе.
4. Разграничивать пользователей Telegram и VK в рамках общей модели аккаунтов.
5. Поддерживать базовую аналитику по источнику: пост, кнопка, меню, рекламная ссылка.
6. Позволять администратору публиковать ссылки на конкретные подборки или категории товаров.
7. Поддерживать уведомление пользователя о смене статуса заказа в доступном канале связи.

## 5. Нефункциональные требования для интеграции с VK и аудитории 800 пользователей

### 5.1. Производительность

1. Система должна выдерживать не менее 800 зарегистрированных пользователей без деградации базовых сценариев.
2. Система должна выдерживать не менее 80 одновременно активных пользователей в пиковые интервалы после публикации в VK.
3. API каталога и карточки товара должно отвечать в пределах 500 мс на 95-м перцентиле при штатной нагрузке.
4. API создания заказа должно отвечать в пределах 1000 мс на 95-м перцентиле без учета внешнего платежного провайдера.
5. Система должна поддерживать горизонтальное масштабирование backend-инстансов без изменения бизнес-логики.

### 5.2. Доступность и надежность

1. Целевая доступность пользовательского API должна быть не ниже 99.5% в месяц.
2. При отказе внешней интеграции VK магазин должен оставаться доступным по прямой ссылке.
3. Ошибки платежного провайдера не должны приводить к потере заказов.
4. Все изменения статусов заказов и платежей должны быть идемпотентными либо защищенными от повторной обработки.
5. Должно выполняться ежедневное резервное копирование базы данных.
6. Время восстановления после критического сбоя не должно превышать 4 часов для MVP-уровня.

### 5.3. Безопасность

1. Идентификационные данные внешних платформ должны проходить верификацию на стороне backend.
2. Административные операции должны быть отделены от пользовательских и защищены отдельным токеном или более сильным механизмом.
3. Система не должна доверять пользовательским идентификаторам без проверки подписи, токена или серверной сессии.
4. Логи не должны содержать секреты, токены доступа и полные платежные реквизиты.
5. Все внешние соединения должны выполняться по HTTPS.

### 5.4. Масштабируемость данных и операций

1. Модель данных должна поддерживать хранение нескольких внешних идентификаторов пользователя: Telegram, VK, web.
2. Архитектура должна позволять добавление новых каналов продаж без переработки доменной модели заказа.
3. Система должна поддерживать каталог не менее чем из 500 товаров без отдельной архитектурной переработки.
4. История заказов и платежей должна храниться не менее 12 месяцев.

### 5.5. Наблюдаемость и сопровождение

1. Для всех ключевых API должны собираться метрики по количеству запросов, ошибкам и времени ответа.
2. Для заказов и оплат должны быть доступны корреляционные идентификаторы для трассировки.
3. Критические ошибки оформления заказа и оплаты должны попадать в alerting.
4. Администратор должен видеть минимальный операционный набор: число новых заказов, неоплаченных заказов, ошибок оплаты и недоступности API.

### 5.6. UX и операционные ожидания

1. Пользовательский сценарий от перехода из VK до открытия витрины должен занимать не более 2 действий.
2. Основной пользовательский путь "открыть магазин -> выбрать товар -> оформить заказ" должен быть адаптирован под мобильные устройства.
3. Ключевые тексты интерфейса должны быть единообразны, без технического жаргона и с понятными статусами заказа.
4. Оператор или администратор должен иметь возможность обработать новый заказ без обращения к разработчику.

## 6. Ограничения и риски

1. В текущем коде проект жестко связан с Telegram-моделью пользователя, поэтому интеграция с VK потребует доработки авторизации и схемы пользователей.
2. Сейчас в проекте используется mock-оплата, поэтому реальный запуск продаж потребует внедрения настоящего платежного процесса.
3. Открытый CORS и простая схема заголовков подходят для разработки, но недостаточны для production-сценария.
4. Тексты в боте и часть пользовательских сценариев выглядят как черновые и должны быть приведены к рабочему тону до запуска.

## 7. Рекомендуемый следующий шаг

Практически следующим шагом имеет смысл оформить техническое задание на "унификацию идентичности пользователя и подключение VK как нового канала", потому что именно это изменение отделяет текущий Telegram MVP от целевой мультиканальной версии.
